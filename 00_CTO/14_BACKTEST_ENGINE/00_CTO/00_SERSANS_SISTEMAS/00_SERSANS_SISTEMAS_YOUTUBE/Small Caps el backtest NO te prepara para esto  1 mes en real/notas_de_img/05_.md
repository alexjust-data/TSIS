# 2. Diferencia entre `Órdenes`, `ActionOrder`, `Trades` y `Trazabilidad`

## Órdenes

Probablemente representa órdenes enviadas al broker:

```text
order_id
symbol
side
qty
type
price
status
route
timestamps
```

## ActionOrder

El término parece específico de DAS.

Posiblemente representa comandos o eventos devueltos por DAS relacionados con la orden:

```text
SEND
ACCEPT
REJECT
CANCEL
REPLACE
PENDING
```

En logs de DAS suelen aparecer precisamente secuencias como:

```text
Sending
Accept
Canceled
Filled
```

La existencia de esta pestaña sugiere que conservan una capa entre:

```text
orden interna del framework
```

y:

```text
evento recibido desde DAS
```

## Trades

La pantalla visible parece mostrar **ejecuciones o fills individuales**, no operaciones completas agregadas.

## Trazabilidad

Probablemente enlaza:

```text
estrategia
→ señal
→ orden interna
→ action order DAS
→ fill
→ posición
```

Esta pestaña podría ser una de las más importantes para ingeniería inversa, porque seguramente contiene IDs cruzados.

# 4. `Estrategia`

Valor visible:

```text
ShortMDL1
```

Esto confirma que cada ejecución conserva la procedencia estratégica.

Campo mínimo:

```text
strategy_id
```

Idealmente también:

```text
strategy_version
strategy_instance_id
```

Esto permite distinguir, por ejemplo:

```text
ShortMDL1_v1
ShortMDL1_v2
```

o dos instancias simultáneas de la misma estrategia.

Para TSIS no bastaría con guardar solo el nombre visible.

# 5. `Lado`

Valores visibles:

```text
Buy
Sell
```

Hay una estrategia llamada `ShortMDL1`, así que la interpretación probable es:

* `Sell`: apertura o incremento de posición corta.
* `Buy`: cobertura parcial o total.

Pero el lado por sí solo no permite saber si el fill:

```text
abre
cierra
aumenta
reduce
revierte
```

Para eso hace falta combinarlo con la posición anterior.

Una app robusta debe registrar:

```text
execution_side
position_effect
```

Ejemplo:

```text
execution_side = BUY
position_effect = CLOSE_SHORT
```

No confiar solo en `Buy/Sell`.

---

# 6. `Notional ($)`

Se comprueba directamente:

```text
75 × 0.9898 ≈ 74.23
```

Por tanto:

```text
notional = quantity × execution_price
```

Es un valor bruto absoluto.

En ventas también se muestra positivo en la columna notional:

```text
Sell 10 × 1.08 = 10.80
```

Así que `Notional` no lleva signo.

---

# 7. `Flujo neto ($)`

La columna sí utiliza signo.

Ejemplos visibles:

```text
Buy 75 → +74.23
Sell 10 → -10.80
```

Esto parece contraintuitivo desde el punto de vista de cash flow convencional, donde una compra suele ser salida negativa de caja.

Probablemente están usando una convención interna como:

```text
Buy  = flujo positivo
Sell = flujo negativo
```

quizá para reconstruir el P&L de posiciones cortas mediante:

```text
ventas negativas + compras positivas
```

o porque el signo representa dirección de inventario y no caja.

No debemos copiar esa convención sin verificarla.

Para TSIS deben separarse:

```text
signed_quantity
cash_flow
notional
```

Por ejemplo:

```text
signed_quantity:
buy  = +qty
sell = -qty

cash_flow:
buy  = -(qty × price + costs)
sell = +(qty × price - costs)
```

La etiqueta `Flujo neto` necesita validación adicional.

---

# 8. `Ruta`

Valores visibles:

```text
ZPRO
ZSTOP
```

Esto es muy relevante.

La ejecución conserva la ruta o mecanismo de orden utilizado.

Probable interpretación:

```text
ZPRO
```

ruta de ejecución DAS configurada para órdenes normales.

```text
ZSTOP
```

ruta o script asociado con stops.

No podemos confirmar la semántica exacta, pero sí afirmar que guardan el valor de route por ejecución.

Campos necesarios:

```text
requested_route
actual_route
```

Porque la ruta solicitada y la finalmente utilizada podrían diferir.

---

# 9. `Liquidez`

Valor:

```text
Taker
```

Esto indica clasificación maker/taker de la ejecución.

Eso es especialmente importante para:

* tarifas;
* análisis de slippage;
* calidad de ejecución;
* selección de rutas;
* agresividad de la estrategia.

Dominio mínimo:

```text
liquidity_flag:
maker
taker
unknown
```

Es posible que DAS devuelva directamente esta clasificación o que ellos la infieran.

# 10. `Tarifas` y `Fees Total`

En las filas visibles:

```text
0.00
0.00
```

La existencia de ambas columnas sugiere que distinguen al menos dos conceptos.

Posible separación:

```text
Tarifas
= comisión específica de la ruta o liquidez
```

```text
Fees Total
= suma de comisiones, ECN fees, SEC/TAF, locate allocation, etc.
```

No podemos saberlo por la imagen.

Para replicarlo bien convendría un ledger de costes desglosado:

```text
commission
ecn_fee
sec_fee
taf_fee
routing_fee
borrow_fee
locate_fee
other_fee
total_fee
```

y no solo un único `fees_total`.

# 11. `PNL` por fila

En algunas compras de cobertura aparece:

```text
13.04
6.67
-12.73
-10.15
29.30
11.70
```

En ventas de apertura aparece:

```text
0.00
```

Esto permite una inferencia bastante fuerte:

> El P&L se reconoce cuando una ejecución reduce o cierra una posición, no cuando la abre.

Ejemplo:

```text
SNAL Sell 10 → PNL 0.00
SNAL Buy 67 → PNL -12.73
```

El `Buy` probablemente cubre posición corta y materializa pérdida.

Esto indica que su accounting usa una lógica de matching entre fills.

No sabemos si usa:

* FIFO;
* LIFO;
* precio promedio;
* lot accounting.

Pero el P&L por fill exige alguna política de asignación.

Para TSIS debe documentarse explícitamente:

```text
position_cost_basis_method:
average_price
FIFO
LIFO
```

En trading intradía, el precio promedio suele ser habitual, pero no hay que asumirlo.

# 12. `Timestamp`

Se ven valores ISO como:

```text
2026-04-13T15:30:00...
```

La parte derecha queda cortada, pero en otras pantallas vimos offset horario.

Esto indica:

* timestamp preciso por fill;
* almacenamiento probablemente serializado en ISO 8601;
* posibilidad de ordenar y reconstruir secuencias.

Un fill profesional debería tener más de un timestamp:

```text
strategy_decision_ts
order_created_ts
order_sent_ts
broker_ack_ts
venue_execution_ts
framework_receive_ts
persisted_ts
```

La pantalla muestra uno, pero la pestaña `Trazabilidad` podría contener los demás.

# 14. `Total: 86`

La pantalla muestra:

```text
Total: 86
```

Eso parece indicar 86 registros de ejecución en el periodo, no 86 operaciones completas.

En el vídeo hablaban de 48 trades cerrados.

Por tanto:

```text
86 fills
```

pueden corresponder a:

```text
48 round trips
```

porque algunas operaciones pueden tener:

* varios fills de entrada;
* varios fills de salida;
* parciales.

Esta diferencia es esencial:

```text
execution count ≠ trade count
```

La aplicación parece respetar esa separación.

# Conclusión técnica

La pantalla no muestra simplemente una lista de “trades”.

Muestra un **ledger de ejecuciones normalizadas** con:

* estrategia originadora;
* símbolo;
* lado;
* cantidad;
* precio;
* notional;
* flujo firmado;
* ruta;
* clasificación maker/taker;
* costes;
* P&L realizado;
* timestamp.

La pista más importante es esta:

```text
Total ejecuciones: 86
```

frente a los aproximadamente:

```text
48 trades cerrados
```

de la pantalla de análisis.

Eso demuestra que el sistema distingue, como mínimo:

```text
execution/fill
```

de:

```text
trade agregado
```

Esa separación debe existir obligatoriamente en la app que construyamos.
