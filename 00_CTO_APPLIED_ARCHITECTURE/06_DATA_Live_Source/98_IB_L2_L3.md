# Conclusión

**Interactive Brokers sí puede proporcionar en tiempo real un libro L2 parecido a MBP-10, pero no ofrece un feed L3/MBO real ni un histórico del libro que pueda reproducirse con el mismo esquema que el live.**

| Requisito                                  |                       IBKR | Veredicto             |
| ------------------------------------------ | -------------------------: | --------------------- |
| L2 MBP-10 en tiempo real                   |       Sí, con limitaciones | **Apto parcialmente** |
| L3/MBO con `order_id` por orden            |                         No | **No apto**           |
| Histórico/replay del L2                    | No como producto histórico | **No apto**           |
| Histórico con el mismo esquema que live    |                         No | **No apto**           |
| Grabar live y reproducir tu propia captura |      Sí, construyéndolo tú | **Posible**           |

## 1. L2 MBP-10 en tiempo real: sí

Mediante la TWS API existe:

```python
reqMktDepth(
    reqId,
    contract,
    numRows=10,
    isSmartDepth=True_or_False,
    mktDepthOptions=[]
)
```

El parámetro `numRows` indica cuántas filas se solicitan **por cada lado del libro**, por lo que puedes pedir diez filas bid y diez filas ask. IBKR devuelve los cambios mediante `updateMktDepth` o `updateMktDepthL2`. ([IBKR Campus US][1])

Los mensajes contienen:

```text
position
operation
side
price
size
marketMaker/exchange, en algunos casos
```

Las operaciones son:

```text
0 = insert
1 = update
2 = delete
```

Esto permite mantener localmente un libro de diez filas aplicando incrementalmente los mensajes recibidos. ([IBKR Campus US][1])

### Ejemplo conceptual

```text
position=0
operation=0
side=1
price=4.25
size=1800
```

Significa insertar una fila en la posición cero del bid. No significa que se haya añadido una orden individual de 1.800 acciones.

## 2. No es un MBP-10 institucional completamente limpio

Aunque funcionalmente se parece a un feed MBP, IBKR introduce varias limitaciones relevantes.

IBKR afirma que los mensajes de profundidad se envían sin el muestreo aplicado al Level 1. Sin embargo, también declara que **no garantiza que aparezca cada precio cotizado** y que las órdenes odd-lot no se incluyen en ese libro de profundidad. ([IBKR Campus US][1])

Esto es importante en small caps porque una parte relevante de la actividad puede producirse mediante tamaños inferiores a cien acciones.

IBKR ha incorporado algunos campos separados para el mejor odd-lot bid y ask en versiones recientes de la API, pero eso no convierte el DOM en un libro completo que incluya todas las órdenes odd-lot ni proporciona profundidad odd-lot multinivel. ([IBKR Campus US][1])

Además, el callback de market depth no contiene un timestamp del mercado:

```text
position
operation
side
price
size
marketMaker
isSmartDepth
```

Por tanto, tendrás que añadir en tu capturador:

```text
local_receive_timestamp_ns
monotonic_timestamp_ns
sequence_number_local
```

Ese tiempo será el momento de recepción en tu máquina, **no necesariamente el timestamp original del matching engine o del feed de la bolsa**. Esto se deduce directamente de los campos publicados por IBKR para los callbacks de profundidad. ([IBKR Campus US][1])

## 3. SmartDepth frente a profundidad directa

IBKR permite dos enfoques.

### `isSmartDepth=True`

Obtienes una vista agregada procedente de los mercados disponibles, parecida al BookTrader de TWS. El campo `marketMaker` identifica normalmente la bolsa que mantiene esa fila. ([IBKR Campus US][1])

Es adecuado para responder a preguntas como:

```text
¿Cuánta liquidez visible agregada existe en los primeros diez niveles?
¿Cómo cambia el imbalance?
¿Se vacía el ask agregado antes de una extensión?
```

Pero no es ideal para estudiar detalladamente:

```text
la cola exacta de NASDAQ
la prioridad dentro de una bolsa
la vida individual de las órdenes
la posición en cola de una orden
```

### `isSmartDepth=False`

La solicitud se dirige a un destino concreto. Dependiendo del mercado, `updateMktDepthL2` puede incluir el MPID del market maker; en otros casos solo se recibe la profundidad del mercado correspondiente. ([IBKR Campus US][1])

Para una investigación seria tendrías que decidir si deseas:

```text
SMART consolidated view
```

o libros separados:

```text
NASDAQ/ISLAND
ARCA
NYSE
BATS
EDGX
IEX
...
```

IBKR no entrega necesariamente en una única suscripción SMART la misma semántica que tendría un feed consolidado institucional normalizado por venue.

## 4. IBKR no proporciona L3/MBO real

Aquí la respuesta es clara: **no he encontrado en la API oficial de IBKR un feed público de Market By Order con identificador persistente por orden**.

En un verdadero MBO esperarías mensajes como:

```text
ADD
order_id=893746238
side=BID
price=4.25
qty=500
priority=...
exchange_timestamp=...
```

Después:

```text
MODIFY
order_id=893746238
new_qty=300
```

Y finalmente:

```text
CANCEL
order_id=893746238
```

IBKR no expone eso. Su mensaje de profundidad tiene `position`, `price` y `size`, pero no contiene:

```text
exchange_order_id
order_priority
queue_position
individual_order_quantity
original_order_id
participant_order_id persistente
```

El campo `marketMaker` tampoco es un `order_id`. Puede representar el MPID o la bolsa, según el tipo de solicitud. ([IBKR Campus US][1])

### Cuidado con `operation=insert/update/delete`

Puede parecer MBO porque existen operaciones incrementales. Pero son operaciones sobre **filas del libro**, no sobre órdenes individuales.

Por ejemplo:

```text
position=2
operation=1
price=4.23
size=6400
```

solo significa que la fila situada en la posición dos debe actualizarse. No permite saber si esos 6.400 títulos corresponden a:

```text
1 orden de 6.400
8 órdenes de 800
una orden nueva y tres cancelaciones
un cambio de prioridad
una ejecución parcial
```

Por tanto:

> **IBKR L2 es esencialmente profundidad agregada/posicional, no MBO.**

## 5. El histórico de IBKR no contiene el libro L2

IBKR ofrece `reqHistoricalTicks`, pero los tipos disponibles son:

```text
Bid_Ask
Midpoint
Trades
```

La solicitud devuelve como máximo 1.000 ticks por petición. ([IBKR Campus US][1])

El histórico `Bid_Ask` contiene aproximadamente:

```text
time
best_bid_price
best_ask_price
best_bid_size
best_ask_size
atributos del bid/ask
```

Es decir, histórico del mejor bid y ask, no diez niveles del libro.

No contiene:

```text
bid_level_1 ... bid_level_10
ask_level_1 ... ask_level_10
insert/update/delete por nivel
market maker por nivel
estado completo inicial del libro
secuencia de market-depth
order IDs
```

Los datos tick-by-tick en tiempo real de IBKR corresponden fundamentalmente a Time & Sales y a best bid/ask. IBKR documenta los tipos `Last`, `AllLast`, `BidAsk` y `MidPoint`, no una modalidad histórica de `MarketDepth`. ([IBKR Campus US][1])

## 6. No existe replay histórico con el mismo esquema que live

Este requisito no se cumple:

```text
Live:
updateMktDepthL2(position, marketMaker, operation, side, price, size)

Historical:
mismos mensajes, misma semántica, misma secuencia
```

IBKR no proporciona una API histórica que devuelva los callbacks de `updateMktDepth` o `updateMktDepthL2` de sesiones pasadas.

El esquema histórico de IBKR es distinto:

```text
historicalTicksBidAsk
historicalTicksLast
historical bars
```

mientras que el live L2 utiliza:

```text
updateMktDepth
updateMktDepthL2
```

Por eso no puedes desarrollar contra un único contrato de datos y sustituir simplemente:

```text
live source → historical source
```

manteniendo una reproducción exacta del DOM.

## 7. La alternativa: crear tu propio histórico desde el live

Sí puedes construir un grabador propio:

```text
IBKR reqMktDepth
        ↓
raw append-only event log
        ↓
snapshots periódicos del libro
        ↓
normalizador
        ↓
replay engine
        ↓
misma interfaz para investigación y live
```

El raw log podría guardar:

```text
schema_version
capture_session_id
symbol
conid
requested_exchange
is_smart_depth
requested_num_rows
local_sequence
local_receive_time_ns
monotonic_time_ns
position
operation
side
price
size
market_maker
connection_generation
reset_generation
```

También debes registrar los resets. IBKR indica expresamente que el error 317 significa que el market depth ha sido reiniciado y que debes vaciar el libro antes de aplicar las nuevas entradas; de lo contrario, el estado local quedaría corrupto. ([IBKR Campus US][1])

Este sistema te permitiría reproducir **tu captura de IBKR**, pero no resolvería las limitaciones originarias:

```text
sin exchange timestamp
sin order_id
sin prioridad de cola
sin odd lots completos
sin garantía de ver todas las cotizaciones
dependencia de TWS/IB Gateway y conexión
```

## 8. Suscripciones y límites

Para market depth necesitas suscripciones Level 2. IBKR diferencia expresamente:

```text
Level 1 → live watchlist, tick-by-tick, barras e historical ticks
Level 2 → market depth
```

([IBKR Campus US][2])

En NASDAQ/ISLAND, el acceso por API puede requerir una combinación específica:

```text
feeds Level 1 de acciones estadounidenses
NASDAQ TotalView-OpenView
NASDAQ TotalView-OpenView EDS para uso off-platform/API
```

La documentación actual de IBKR señala específicamente el requisito EDS para obtener esos datos mediante API o plataformas de terceros. ([IBKR Campus US][2])

IBKR también limita las suscripciones simultáneas de market depth. Con la asignación básica de cien líneas de mercado, la tabla oficial indica normalmente un máximo inicial de **tres solicitudes simultáneas de Level 2**. El límite aumenta según líneas de mercado, patrimonio, comisiones y quote boosters. ([IBKR Campus US][2])

Esto puede ser un problema serio si pretendes capturar el L2 de muchas small caps simultáneamente.

# Veredicto para TSIS

## IBKR serviría para

```text
prototipar features L2 en tiempo real
medir imbalance de los primeros niveles
estudiar spread y depth visible
detectar retirada agregada de liquidez
capturar unas pocas acciones seleccionadas
construir un recorder económico para investigación inicial
```

## IBKR no serviría como fuente científica principal para

```text
reconstrucción histórica del libro
backtesting L2 sobre años de datos
queue modelling
cancel/add behaviour por orden
order lifetime
spoofing basado en identidades persistentes
MBO/L3
replay histórico idéntico al live
investigación reproducible con timestamp de exchange
captura simultánea de un universo amplio de small caps
```

Mi clasificación final sería:

```text
IBKR L2 live MBP-10:          SÍ, con reservas importantes
IBKR L3/MBO:                  NO
IBKR historical L2 replay:    NO
Mismo esquema historical/live:NO
Recorder propio desde live:   SÍ
Fuente institucional TSIS:    INSUFICIENTE
```

Para el tipo de infraestructura que estás planteando, IBKR puede utilizarse como **broker y fuente auxiliar de live L2**, pero no sustituye a un proveedor de datos de microestructura que entregue histórico MBP/MBO normalizado y replayable.
